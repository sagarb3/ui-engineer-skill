# Design Brief and Exploration

Use this guide to establish a direction, compare concepts, or decide the first-screen structure. Continue an approved direction without reopening selection unless new requirements invalidate it.

## Establish Product Facts

Identify the product, audience, main task, frequent use conditions, primary device, supported range, existing identity, available assets, and delivery format. Separate confirmed facts from unknowns. Ask about missing requirements before proceeding; do not turn a reference product's audience or workflow into an assumption about this one.

For an existing product, inspect the current route, adjacent screens, components, design rules, and actual user content. A redesign may change hierarchy while retaining navigation and brand. A feature addition normally retains the current direction. Determine which kind of work was requested.

Use a compact working brief rather than an unnecessary document:

```text
Task: Help warehouse staff identify and resolve low-stock items.
Primary surface: A desktop inventory queue; narrow screens remain usable.
Priority: Exceptions first, then the information needed to resolve them.
Preserve: Existing navigation, component library, and brand colors.
Interaction: Select an item, inspect its stock history, create a restock request.
Evidence: Rendered queue, selected-item state, and a completed request flow.
```

Ask about unspecified workflow details; this example does not define another product's requirements.

## Learn From Actual References

When reference research is part of the request, inspect real screenshots or accessible pages. Separate visual evidence from interaction evidence. A screenshot can show density and hierarchy; it cannot prove what happens after submission.

For each useful reference, identify a relationship worth adopting: where the main object appears, how the important action is placed, how secondary information recedes, how states connect, and which conventions users already recognize. State what should change for the current product. Do not copy another product's brand, copy, proprietary assets, or unrelated feature structure.

If a page cannot be inspected, label the missing evidence. Do not write a confident visual analysis from memory. Use another accessible reference when that fits the task rather than repeatedly retrying the same blocked page.

## Develop a Product-specific Concept

Translate vague requests into visible decisions. "Professional" might mean a restrained type hierarchy, compact data alignment, and clear status labels in one product; another may need a bold editorial layout. Ask if the intended meaning remains unclear.

Find a useful organizing idea in the product's objects, actions, setting, or audience. A route-planning tool can emphasize spatial relationships; an audio editor can make the waveform the working surface. Do not add a physical metaphor that makes the actual task harder.

For each concept, identify a central object, a principal action, the visible result, and one distinctive moment. That moment may be a meaningful comparison, a completed upload joining a collection, or a clear before-and-after view. It need not be an animation. Distinctiveness should come from the product rather than decorative novelty.

Where authorized independent concept work is available, provide facts and constraints without supplying the preferred answer. Otherwise compare alternatives yourself and describe the work as self-assessed. Do not claim independence or create extra agent work merely because this guide mentions it.

## Choose the First-screen Structure

Choose structure before filling a default heading-description-button template. Match the user's reason for arriving:

| Page purpose | Plausible structure | Question to resolve |
| --- | --- | --- |
| Process work | Compact context bar and an immediately usable work surface | Are the object, exception, and next action visible together? |
| Browse a collection | Search, scope, and the first useful set of objects | Does introductory content push the collection out of view? |
| Read or learn | Clear entry, reading hierarchy, and supportive navigation | Is the text comfortable to read rather than merely impressive? |
| Evaluate a product | Product demonstration, evidence, or a focused proposition | What must the visitor see to trust the claim? |
| Experience a brand or exhibition | Image-led, type-led, or object-led composition | Can the visual idea carry the content without obscuring the action? |
| Manipulate a canvas | The canvas and contextual tools | Does framing compete with usable working space? |

For a persuasion page, consider a single dominant object, an editorial opening, a full-width demonstration, a typographic statement, an evidence-led layout, or a split layout justified by its content. No one arrangement is mandatory. Do not force a dashboard into a marketing hero or force a product story into identical cards.

Sketch the major regions in grayscale. Locate the reading start, main object, primary action, supporting evidence, and resulting state. If hierarchy only works after adding bright color, refine the structure first.

## Write a Direction Card

Record the design intention; main object and action; first-screen layout; below-fold progression; text roles; color roles and their product basis; imagery and sourcing; icon and control treatment; important interaction; motion if justified; supported devices; and implementation dependencies. Keep it in the existing task notes unless a design document is requested.

Identify asset availability and engineering cost before proposing an asset-dependent concept as feasible. Do not promise a distinctive 3D interaction that depends on unavailable models or an unapproved rendering stack.

## Compare Fairly

Create alternatives only when requested. Use the requested count; ask if the number materially changes the work and is unspecified. Keep product facts, required content, target viewport, and core task comparable. Preserve brand constraints across all options.

Vary meaningful design choices: composition, density, image role, typographic hierarchy, interaction organization, and emphasis. Light, dark, and warm versions of the same skeleton are theme variations, not necessarily separate concepts. For a layout-only comparison, keep typography and palette fixed so the layout decision remains clear.

Reject an option if it violates the brief, hides the main action, needs unavailable assets, or only exists to make the preferred option look good. Check alternatives in grayscale and at actual reading size, not just as attractive thumbnails.

Use a neutral comparison surface with clear candidate names and a baseline for existing-product changes. Show the same scale, content state, and viewport. Screenshots must be labeled static; interactive previews must be identified as such. Avoid comparison chrome that becomes part of the product design.

Record the selected candidate and revision when the user chooses. Check a later selection against the current set rather than implementing an obsolete option. Continue only the selected direction; do not finish every candidate unnecessarily.

## Verification

- The chosen concept follows confirmed product facts and constraints.
- The first screen communicates the task, main object, and next action.
- Alternatives differ on the dimension actually being compared and remain feasible.
- Unresolved choices were clarified; visual and interaction evidence are distinguished.
- No project-specific material, branding, or source text was copied from a reference.
